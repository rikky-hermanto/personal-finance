Bank Statement Ingestion — end-to-end sequence

One Superbank PDF: drag-and-drop → LLM extraction → categorization → dedup → rows in Postgres
request response ▮ loop / opt ▮ alt branch ┄ Observer (Langfuse/OTel)

The use case: the user drops superbank-2026-07.pdf into the Cashflow upload wizard. It is a PDF with no deterministic layout, so it takes the LLM branch — the most complete path through the pipeline. A BCA or Wise CSV would follow the identical shape with steps 10–15 replaced by a single in-process BcaCsvParser.ParseAsync() call and no AI-service hop at all.

Two HTTP requests, not one. POST /upload-preview parses and returns rows for human review without writing anything; POST /submit is what actually persists. Nothing reaches transactions until the user clicks submit — that is the design, and it is why deduplication runs twice (once to tag rows amber in the preview, once as a hard filter at insert time).

Deduplication is three-tier. Tier 1 is the SHA-256 file hash checked against uploaded_files at step 4 — the same file twice returns 409 Conflict before parsing costs anything. Tiers 2/3 are the composite key (date, amount_idr, description, account_name, flow, bank_running_balance) matched against a ±1-day window of existing rows, plus an in-batch pass so a file that repeats a row internally doesn't import it twice.

Categorization runs inside the parser, not after it — every parser ends with CategorizeBatchAsync(), which resolves in four layers off two Supabase reads: description cache → remarks cache → 106 user rules (longest keyword first) → preset dictionary. Rows nothing matches stay "Uncategorized" and the user can hit ✦ Suggest in the preview for an LLM pass before submitting.
