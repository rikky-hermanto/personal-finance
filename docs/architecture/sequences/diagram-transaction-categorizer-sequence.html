Transaction Categorizer — upload-time engine + manual LLM suggestion sequence

Two live paths in one user journey: the deterministic 4-layer engine at upload, then the "Suggest" LLM fallback
User Frontend .NET API CategoryRuleService Supabase PG AI Service LLM Provider Observer

Use case: a user uploads a BCA CSV statement. The parser runs every row through the 4-layer deterministic engine (history cache → rule match → category presets) with zero LLM cost — CategoryRuleService.CategorizeBatchAsync (CategoryRuleService.cs:41-177). Rows the engine can't resolve stay "Uncategorized". The user then clicks "Suggest" on those rows in TransactionPreview.tsx, which is the one live path that reaches an LLM — POST /api/transactions/categorize-preview → ILlmSuggestionClient → Python /suggest-categories → MerchantSuggester.suggest_batch (app/services/merchant_suggester.py:71-111), Gemini gemini-2.5-flash primary via structured extraction.

What closes the loop: the AI service strips PII from any LLM-suggested keyword (_is_pii_keyword) before returning suggestions; the .NET API maps them to CategorizePreviewResult; the frontend patches editedTransactions in place and shows a suggestion chip per row — nothing is persisted until the user confirms the import.

⚠️ Two things this diagram deliberately does not show as connected, because they aren't wired in the code: (1) TransactionPipelineService.ApplyLlmCategorizationAsync (the automatic Layer-3 ILlmCategorizationClient → POST /categorize fallback) only runs inside upload-preview-new, which is a dormant PF-S11 stub — the live upload-preview endpoint never calls it. (2) POST /categorize-agent (the smolagents ToolCallingAgent ReAct loop, PF-AI007, app/agents/categorizer_agent.py) is a fully standalone Python endpoint with 3 tools (rule search, pgvector similarity, category vocabulary) — no .NET client or frontend UI calls it yet.
