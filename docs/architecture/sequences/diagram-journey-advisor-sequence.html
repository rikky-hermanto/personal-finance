PF-AI008 — Financial Health Advisor: request/response sequence

One fulfilled turn of POST /advisor — from user question to grounded answer
User Frontend AI Service LangGraph Claude .NET API Supabase/PG Observer
Alternative to success · fresh session · Observer can be enabled independently.

Only an exception caught around llm.invoke() takes this path. Tool/API failures do not explicitly set state.error in the current ToolNode wiring. Exceptions escaping the graph reach the route's 502 advisor_error handler instead.

Use case: user asks "Gimana kondisi keuangan saya bulan ini?" in the advisor chat. The agent doesn't have the answer up front — it decides which of its 4 tools to call, fetches real pyramid + cashflow data from the .NET API (backed by Supabase Postgres), reasons over the results, and only then answers. The amber box is the ReAct loop (agent → tools → agent) from financial_advisor.py — it runs once per tool the model decides it needs, twice in this example.

What closes the loop: should_continue checks state.error first and routes to fallback → END when set. Otherwise, it checks the last message for tool_calls; once Claude replies with no further tool calls, the graph exits to END, MemorySaver checkpoints the full state under thread_id = session_id, and AdvisorService returns {answer, session_id, steps_taken} to the caller.

Explore failures: enable ↪ Fallback and choose which Claude call fails. The sequence keeps the completed steps and replaces the remaining success path with call_agent → should_continue → call_fallback → END. The fallback appends a fixed apology (currently including technical error detail), clears the error, and returns it as the answer in an HTTP 200 response. It does not invoke another model. Disable the toggle to restore the success flow.
